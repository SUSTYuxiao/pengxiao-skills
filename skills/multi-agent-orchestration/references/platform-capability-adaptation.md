# 降级适配（仅当宿主与范式假设不符时使用）

范式默认假设宿主支持：持久自定义 Agent、每 Agent 模型选择、并行子任务。多数现代 Agent 工具满足。按 [SKILL.md](../SKILL.md) 应用时先核验并发能力；只有确认某项能力缺失时才按下表降级。

| 缺失能力 | 降级方式 |
| --- | --- |
| 持久自定义 Agent | 将三角色职责、模型层级、只读约束写入 AGENTS.md 规则块末尾，由主智能体内联扮演派发 |
| 独立模型路由 | 全部沿用宿主默认模型；用短提示、轮次上限、最小工具集控制 lite/runner 成本 |
| 并行子任务 | 仅将原本需要并行的角色任务按依赖顺序执行；不额外引入角色，`reviewer` 仍按风险触发 |
| 工作空间隔离 | 串行写入并显式划分文件所有权，禁止两个任务改同一文件 |
| 工具/权限策略 | 在角色提示词中写明禁止操作并由主智能体审查调用；明确标注这是行为约束而非权限隔离，高风险操作不下放 |

## 判断能力是否缺失

按顺序查，找到答案即停止：

1. 宿主的 Agent/设置页面或已有 Agent 配置文件。
2. 宿主官方文档中关于子智能体、模型选择的章节。
3. 都查不到时按缺失能力降级，并在交付中注明证据边界。单次调用失败、当前会话未暴露派发工具或配置暂未刷新，不足以判定宿主永久缺失能力。

## 并发能力检查

检查结果必须区分三件事：宿主支持什么、持久配置写了什么、当前会话实际加载了什么。按以下顺序收集最小证据：

1. 核对宿主及版本，查看该版本的官方文档、配置 schema 或原生设置；确认并发字段的合法名称、取值范围、作用域和加载方式。字段名不能跨宿主硬编码套用。
2. 确认上限统计口径：是否包含主会话、已完成但未关闭的实例是否占槽位、关闭或回收如何释放槽位；同时检查当前实际占用。不能只凭某次创建失败反推默认上限。
3. 检查当前会话暴露的派发工具和同角色多实例能力；用至少两个互不依赖、无副作用的任务验证并行执行、任一完成后的回收与继续派发。复用已有角色探针即可，不为探测上限制造一批无效任务。
4. 记录配置值与探针观察的差异。某次只观察到 4 个并发，不代表所有版本或宿主默认都是 4；本地 Skill 副本较旧，也不能单独证明它是并发不足的根因。未暴露工具、缓存未刷新和永久缺失能力应分别说明。

## 用户已授权时提高上限

1. 确认用户授权覆盖具体配置文件及并发字段；若用户只要求补规则或改 Skill，先交付规则改造，不把它扩大为修改运行时配置的授权。
2. 依据当前宿主版本的文档或 schema 核验字段和统计口径后，比较当前值与目标：目标总并发为 8；上限包含主会话时最多 7 个子智能体，上限仅计子智能体时对应目标为 7。宿主硬限制低于目标时遵守其限制；现有上限高于目标时不因本流程降低。未经验证的字段不写入，缺少证据则说明待核验项。
3. 只修改已授权的并发字段，保留其他设置、角色权限和模型映射，不联动修改共享环境或其他宿主。写后用宿主支持的配置校验方式检查解析结果。
4. 按宿主加载机制重载或在新会话验证；当前会话未重载时只能报告“持久配置已修改，运行时待验证”，不能宣称当前上限已经生效。配置值正确与实际并发探针通过应分别报告，不为证明总上限而强行占满槽位。
5. 主智能体仍按有效工作流和可用槽位调度，常规目标为 2–4 个有效子任务。提高上限是提供余量，不是要求用满名额；满额时先收结果并释放槽位，再继续派发，不能盲目重试。

字段、统计口径或加载方式随宿主版本变化时，原先核验结论失效，重新执行上述检查；不得把过往机器上的配置当作当前宿主契约。
