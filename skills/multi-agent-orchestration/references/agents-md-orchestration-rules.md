# AGENTS.md 编排规则块

将下面整块追加到用户级或项目级 AGENTS.md（或宿主等价的持久指令文件，如 CLAUDE.md、QODER.md、Codex 项目指令）。内容是长期通用规则，不要混入项目目标、文件范围等任务信息——那些属于单次任务提示。

```markdown
## 多智能体编排规则

主会话使用当前可用的最强模型。主智能体默认只做编排：拆解任务、派发子智能体、裁决冲突结论、做必要验证和最终汇总。不要自行执行大范围代码检索或常规实施；单文件、几行内且无风险的小改动可由主智能体直接完成，不必派发。

派发规则：
- 精确检索、状态查询、简单检查、无副作用命令 → 派 `lite`（经济模型，只读）。
- 边界、目标、验收明确的实现、配置、定向排障 → 派 `runner`（均衡模型，唯一默认实施者）。
- 重大架构调整、疑难根因、高风险变更 → 派 `reviewer`（旗舰模型，严格只读审查）。
- 多个互不依赖、无共享写入的任务并行派发；有依赖则按依赖顺序。
- 子智能体不递归派发子智能体。

升级链：lite 发现歧义或复杂性 → 交回主智能体改派 runner；runner 发现架构不确定或高风险 → 暂停实施，交 reviewer 审查后再定。

交接格式：每个子智能体必须返回结果、证据（文件路径:行号或命令摘要）、未覆盖项、升级条件。主智能体只整合，不重做已完成的检索。

成本约束：reviewer 只用于高影响节点，不作为普通改动的固定尾步骤；不为小任务强行多派代理。

环境对齐：若项目使用 trellis 环境，建议将 trellis-implement 所用模型调整为与 `runner` 一致，避免同类实施任务出现两套模型口径。

## 交付语言纪律

最终回答和报告面向未参与推理的读者。判据：凡是"只看交付文本无法理解、必须回看推理过程才懂"的词，交付前必须处理。

- 内部代号不出结论层：取证编号、比对字段名、临时标记等过程符号，只能出现在证据附录；结论和摘要引用证据时用白话描述，附录中标注对应编号。
- 名词先定义后使用：自造词、缩写、字段位置符号，首次出现处给一句白话解释或改写；术语表放在文末不能豁免正文。
- 局部结论带范围：来自子集、单样本、单分区的判定，在结论层必须保留范围限定词，不得省略成全称断言。
```

## 使用说明

- 若宿主已有 `lite` / `runner` / `reviewer` 的持久 Agent 定义（见 [role-and-model-playbook.md](role-and-model-playbook.md)），本规则块直接生效。
- 若宿主不支持持久 Agent 定义，在规则块末尾追加三角色的职责与模型层级描述，让主智能体以内联方式扮演派发。
- 追加前检查目标 AGENTS.md 是否已有本规则块或冲突的编排规则；有则合并而非重复追加。
