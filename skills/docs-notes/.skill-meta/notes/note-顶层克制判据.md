# 顶层克制判据：结构约束进顶层，能力补丁放低处

状态：active
范围：本 skill 全部条款与机制的新增 / 修改决策；同样适用于设计其他 skill 与规范
核验日期：2026-09-16

证据：
- 2026-09-16 本仓 0.3.0 瘦身 diff：接入流程 8 步收 4 段、note 骨架 10 字段改 4 要素必备其余按需、修复模板默认 active 与"未核验保持 pending"矛盾、superseded 放宽、删除重复外置模板
- 用户定调原话（2026-09-16）："在结构设计和流转链路等顶层设计做好克制、精简……不要过度拟合，有时候一些问题是模型能力问题，模型后面会迭代发展，我们做好不变的顶层优雅设计"

问题：一条新规则 / 新机制该不该进顶层规范？

结论：先过三问——
1. **结构约束还是模型能力补丁？** 结构约束（docs/notes 分界、查重判据、自包含、安全边界）不依赖模型强弱，进顶层；防当前模型犯错的细则会随模型迭代变成噪音，写轻（一句原则）或进 note 带失效条件。
2. **模型两年后还需要这条吗？** 需要 → 顶层；不需要 → 补丁，放低处。
3. **载体是终点消费者还是自分发产物？** 终点（项目）可选托管更新，自分发（skill）必须自包含（详见 note-载体与托管边界）。

单案例失败催生的规则默认按过拟合处理：先写轻，反复真实复现再升级。

决策：0.3.0 据此执行（见证据）；防御性长句在防不会发生的事的，删除或压成一句。

替代方案：为每种可预见的误用加防御条款（放弃——堆积成噪音，且防不住新误用形态）。

代价：个别场景误用时无硬条款拦截，靠判据与示例引导；判据依赖维护者的判断力。

失效条件：判据被用户推翻；或模型能力退化导致轻写的规则在真实任务中反复出错、验证补丁确有必要硬写。
