# 载体与托管边界：项目可选托管，skill 必须自包含

状态：active
范围：本 skill 接入目标（项目 / skill）的载体选择与更新方式；不涉及规范内容本身
核验日期：2026-09-16

证据：
- 2026-09-16 本仓提交 20d345e：三个 skill（reading-edition、playlog-one-person-v3-check、fy27-weekly-report）撤销 DOCS_NOTES.md 托管副本与标记块，改为自维护约定
- 用户裁决原话（2026-09-16）：skill 本身内容进 git，托管规范会跨设备应用造成割裂和不一致

问题：托管更新协议（marker 块 + 版本标记 + 按旧模板合并）该不该随规范进入 skill？

结论：不。分界是**载体是否选择持续接收上游规范更新**：
- 项目是终点消费者，可以自愿托管——它想收上游更新，且合并协议由 docs-notes 接入器在用户机器上执行。
- skill 是会自我分发的 git 产物（随 clone / pskills light 拷贝复制），托管块引入第二维护通道：版本标记在无接入器的机器上永不过期成装饰，"分发源"指针跨设备悬空，git 单通道与外部协议更新互相打架。

决策：接入其他 skill 只发六行自维护约定（无标记、无版本、无分发源），复制后即目标自有内容，由目标 git 维护。

替代方案：skill 也托管（放弃——双维护通道，见结论）；公共 md 跨仓引用（更早放弃——违反 skill 自包含分发约束）。

代价：上游自维护约定演进时不自动传播到已接入 skill，靠各 skill 维护者按需手动对照。

失效条件：出现"约定必须跨所有 skill 强一致传播"的真实需求时重议；届时优先考虑 pskills 分发层方案，而非恢复文档托管。
