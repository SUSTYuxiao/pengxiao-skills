# docs 专项写作参考（写 / 改 docs 时按需读）

本文件是写法参考，不是目标项目运行依赖。核心职责与维护规则在 `DOCS_NOTES.md`，此处只补具体写法、好坏例子、边界与验收。不复制到目标项目。

**以下示例均为虚构写法示例，不代表任何目标项目事实；接入时替换为真实内容与链接。**

## 1. 写什么

`docs/` 只记**当前事实**：目标、边界、架构、模块、操作、限制。读者应能在不复述历史的前提下回答"现在是什么、怎么用、限制在哪"。

**好例子（虚构示例）**

```markdown
## 采集入口

`example_collector.py` 独占外部调用与响应校验；预览层只管理正文版本与退避，不发起调用。
边界：新增来源只在采集层注册；预览层不感知来源差异。
限制：单次最多回填 {{N}} 条，超限丢弃并记 {{事件名}}（待验证）。
```

事实明确、边界可执行、未核验处显式标注。

**坏例子（虚构示例）**

```markdown
## 采集入口

我们曾尝试用 A 方案，后来讨论认为 B 更好，最终改成现在的实现，原因见下。当前实现大体可用。
```

夹带历史论证、"大体可用"无法验收。

## 2. 入口与分层

- 入口先写目标、边界、架构、契约、操作、限制，再链专题。
- 专题一文档、短小直白，只写当前事实；过期内容直接改写，旧版论证去 notes。
- 入口只在"契约"处给一句话概述并链接 `spec/`，不复制契约全文；因果与证据链接到 `notes/`。

**好例子**：入口 `限制` 段写"仅支持单机，无并发写入"，并链接 `spec/concurrency.md` 的并发契约。

**坏例子**：入口整段抄入并发契约、失败语义与测试命令。

## 3. 边界与验收

- 只写当前事实；产品路线等计划内容标"计划 / 未验证"与生效边界。
- 不写任务计划、执行日志、会话记录，也不写"待办清单"式内容。
- 验收：读者只看 `docs/` 能说清目标、边界、操作、限制；无悬空链接；未核验处显式标注；契约与证据只链接不复制。
- 事实改变即改 `docs/`，并在 `notes/` 留因果；不要为保历史而在 docs 里并列新旧两版。
