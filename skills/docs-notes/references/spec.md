# spec 专项写作参考（写 / 改 spec 时按需读）

本文件是写法参考，不是目标项目运行依赖。核心职责与维护规则在 `DOCS_NOTES.md`，此处只补具体写法、好坏例子、边界与验收。不复制到目标项目。

**以下示例均为虚构写法示例，不代表任何目标项目事实；验证方式、失败语义与失效条件接入时必须替换为真实可复现内容。**

## 1. 写什么

`spec/` 只记**当前必须成立、且可验证**的契约、不变量与失败语义。愿望、方向、未核验判断不写进 spec。

**好例子（虚构示例）**

```markdown
# 单源采集失败保留旧缓存
类型：失败语义
范围：仅单源刷新；全量重启不适用
内容：单源刷新失败时，该源上一份成功快照继续对外可读，`updated_at` 不推进。
验证：mock 单源超时后断言接口仍返回旧条目，且 `updated_at` 不变。
失败语义：若清空旧条目，视为契约破坏，接口返回空并记 {{事件名}}。
失效条件：改为无缓存直读时本契约作废。
```

可复现、含失败表现与失效条件。

**坏例子（虚构示例）**

```markdown
# 采集应该稳定
内容：系统要尽量不丢数据，提升用户体验。
```

不可验证、无范围、无失败语义。

## 2. 更新与验证

- 契约变化时同步改内容、验证方式与失败语义，三者不能只改其一。
- 验证方式写命令、测试、查询或可复现观察，不写"人工确认无误"。
- 一条一义；复合承诺拆成多条或拆文件，避免部分失效无法标注。
- 失效契约原位标失效或迁移，保留历史链接；不在 spec 里留半失效整段。

## 3. 边界与验收

- 不写实现方案、历史争论、任务计划；这些去 docs 或 notes。
- 不把未验证结论升级成 active 契约。
- 验收：每条契约都有范围、可复现验证与失败语义；入口列全主题并可跳转；无愿望式措辞（"尽量"、"应该会"）；失效条件明确。
