# 设计约束：本 skill 如何迭代（维护者视角）

本文件约束 reading-edition skill 自身的迭代方式，供未来迭代本 skill 的 agent 遵守。它不约束 skill 的使用方式——那是 SKILL.md 与 references/ 的事。以后迭代以本文件为准，不得漂移回「主文件膨胀」。

## SKILL.md 保持指令级克制

- 参照系是 eli5（~/.agents/skills/eli5/SKILL.md，13 行）：一句定位 + 占位符，全部执行细节交给模型智力。
- SKILL.md 只放三样东西：一句定位（含与 eli5 的分工）、词级别的本质要求（受众自适应、结论前置、按需折叠、信息零丢失、单文件自包含、措辞客观、md 唯一事实基线）、references 按需读取指引。
- 每加一行都要过「删掉损失什么」测试：删掉后模型大概率做错的方向性内容才留下；怎么做（配方、清单、示例、参数）一律下沉 references/。
- 来历：0.1.0 版曾把三组原则明细直接写进 SKILL.md（31 行），被用户判定为噪声——细则在主文件里出现，模型会把「参考要点」当成「必须逐条执行的流程」，灵活性反而被挤掉。此后重构为 0.2.0 的十几行形态，约束为不超过 20 行。

## 一步到位执行模型

- skill 的执行模型是单次会话一步到位：自设目标（受众判断、结构规划）→ 生成 → 按需读 references → 自检（rigor.md）→ 自修正 → 一次性交付。不预设用户多轮反馈来回改。
- 「多轮演进」只存在于本 skill 的来源历史（case-20260826.md 的 V0→V6），其教训已全部提炼为单次执行内的生成要求与自检项。历史不是模型：不得把「md 改则 HTML 跟随」之类的同步协议重新升格为主框架，它只作为 rigor.md 里的边界情况小节存在。

## references/ 组织

- 每文件单一场景，文件头一行「适用场景」，让模型按需加载而不是全量读取。
- 当前分工：generation（生成阶段）／rigor（交付前自检）／wording（措辞客观化）／folding（按需披露）／publishing（语雀发布）／case-20260826（案例档案）。

## 案例档案是防漂移锚点

- case-20260826.md 记录六轮演化的用户反馈原话与教训来源。任何原则被质疑「为什么存在」时，先查案例档案；任何新原则入 skill 前，先问它在案例里有没有事实支撑。
- 案例中的用户反馈原话（「过度比喻」「篇幅过大」「读者有技术背景」等）不得改写弱化——它们是原则的证据。
