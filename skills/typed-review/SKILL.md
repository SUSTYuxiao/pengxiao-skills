# typed-review：把审核要求变成可重复执行的检查

用户说“发布前按我的标准检查”，本 skill 将这些标准写成 YAML，再用固定的 Python runner 执行。**规则由 agent 根据用户诉求设计，判断由模型提供，是否需要修改由回到原文的复核决定。** 这里的“静态”指规则保存在文件中，不表示检查结果是确定性证明。

## 先分清本次要做什么

| 用户诉求 | 执行动作 | 交付 |
|---|---|---|
| 建立审核工作流 | 读对象与要求，设计规则，验证配置 | YAML + 原样复制的 `references/runner.py` |
| 用已有规则检查 | 读取 YAML，确认输入和端点，执行 runner | 检查结果与经原文核对的问题 |
| 调整误报、漏报或阈值 | 对照标注样本，先查输入与问题，再回放阈值 | 更新的 YAML、对比结果和剩余限制 |

已有配置能完成任务就复用，不重新生成脚本。只要求审阅时不擅自改原文；没有要求保存审核包时，可直接用本 skill 的 runner，不必给项目增加文件。

## 从诉求生成规则

先读审核对象，确定用户要判断什么、给谁看、哪些材料能支撑判断。已有上下文够用就执行；缺少会改变判断的证据时标明限制，不让模型凭空补齐。

1. **准备模型真正看得到的材料。** 当前 runner 只读本地 UTF-8 文件，每条规则引用一个输入。需要对照需求与代码、事实材料与报告时，在获准的工作目录准备有明确标签的合并输入；多个 `inputs` 不会自动合并。代码 diff 需先自行导出，runner 不负责读取 Git。
2. **把宽泛标准拆成具体问题。** 例如“报告是否靠谱”应拆为“结论是否超出材料范围”“数字与结论之间是否缺少解释”。一条规则尽量只问一个问题；不要因模板有五个槽位就强塞五条规则。
3. **选择答案类型与判定方向。** 是否存在某问题用 `noul`；互斥类别用 `choice`；有明确定义的等级用 `score`。问题、阈值和结果提示必须同向，例如“存在越界结论”的高分才表示问题。`confidence` 不等于选项概率，也不等于严重程度。
4. **按契约写 YAML。** 先读 `references/schema.md`，只使用 runner 已支持的字段。`message` 写“要复核什么”，不要伪装成模型生成的原因。新规则默认 `warning`，阈值标为未校准；用户有既定标准时保留并说明。
5. **交付可搬走的审核包。** 用户要求留文件时，在指定目录放 YAML 和原样复制的 runner；输入路径相对 YAML 或运行时覆盖。无需安装本 skill 或 reader-first 即可执行，但仍需 uv、脚本声明的依赖和可用模型端点。不复制业务原文进 skill，不为每份规则重写 HTTP 客户端。

`examples/reader-first.yaml` 是五条写作底线的候选问题示例，不是所有审核任务的默认清单。用于 reader-first 时按读者和材料裁剪；一个底线可以拆成多条检查，不能由“覆盖五条”推导出审核完整。

## 执行检查

先定位本 skill 的实际目录，不假定工作目录在仓库根。将下面变量替换为本次实际绝对路径：

```bash
SKILL_DIR="/absolute/path/to/typed-review"
CONFIG="/absolute/path/to/review.yaml"
INPUT="/absolute/path/to/report.md"

# 校验配置、读取输入并预览计划；退出码 3 表示未发送，不是失败
uv run "$SKILL_DIR/references/runner.py" "$CONFIG" --input "report=$INPUT"

# report 必须是该 YAML 中存在的输入 ID；推荐端点传根地址；完整 /v1/systemone 地址也会自动归一化
uv run "$SKILL_DIR/references/runner.py" "$CONFIG" --input "report=$INPUT" \
  --base-url "$JEV_BASE_URL" --send --format json
```

YAML 配置模型、超时和并发数；认证及命令行覆盖见 schema。用户明确指定端点时优先用于本次执行，不因环境变量为空而降级，也不自动持久化地址。用户已要求真实检查时可直接执行，不追加隐私审批；数据安全责任见 `README.md`。默认 dry-run 是预览功能，不是审批流程。

runner 每条规则发一个请求，用有上限的并发执行。它没有自动分段、Git 收集、外部事实检索、原文行号定位或自动调参能力；输入过大时应显式缩小范围或准备分段文件，不能静默截断后宣称全文通过。

### 长文覆盖范围是前提

提交完整文件不代表模型读到了全文。服务的输入长度限制、截断行为或统计口径未确认时，结果必须标记为“输入覆盖未确认”，不能称全文通过；即使返回全部 pass 也一样。多份长文的 `input_tokens` 总停在同一值是排查线索，不单凭它认定具体截断长度。

优先核验端点限制和输入处理；需要分段时保留章节、对象与必要证据上下文，记录每段覆盖范围，全文结构仍由传统审阅补齐。未完成这一步时保留模型结果作辅助线索，不凭分数调整全文质量阈值或阻断发布。当前这些是执行 skill 时的约束，runner 尚未自动检测截断或输出覆盖状态。

## 校准：先验证程序，再验证判断

- **mock 验证程序。** 构造响应以覆盖 pass、flag、uncertain、缺字段、请求失败及边界分数；它不能证明模型能识别真实问题。
- **正反例验证规则。** 可先用标明“合成”的正反例发现方向写反、问题过宽等缺陷；效果评估仍要有人工标注的真实材料。记录每条问题的预期、依据与模型分数；没有样本时如实交付未校准版本。
- **先排查材料和问题，再调阈值。** 缺上下文、问题含糊或实际模型变更时，不能靠移动阈值掩盖问题。runner 返回的实际模型应一并保留；它不一定等于请求的模型名。
- **用回放选阈值。** 保留规则/输入版本、人工标签和原始结果；在一部分样本上比较误报、漏报与不确定比例，再用未参与调参的样本验证。当前 runner 不提供校准命令，由 agent 对保存结果做对比；若改问题或模型，重新推理，不能沿用旧分数。

默认数值只是便于跑通的起点，详见 schema；不是可靠性保证。样本数量和容错标准随风险决定，不能把“正反各 20 例”当作启用阻断的通用门槛。未校准时保持辅助审阅；不要为了让当前文章通过而调参，也不要为了显得保守把全部结果推入不确定区。

## 把结果变成读者能用的结论

- `flag` 是命中规则的候选问题，`uncertain` 是暂不能判定：回到原文找对应片段，并解释为什么需要处理。模型不生成理由；不得把 YAML 的固定提示当作定位证据。
- `pass` 仅表示本次输入未命中该配置的问题，不证明事实正确或已覆盖全部风险。
- `error` 是执行失败，`not_sent` 是未执行；都不能写成通过。报告检查范围、实际模型、有效结果和未覆盖项，不只报一个“通过率”。
- 退出码 `0/1/2/3` 分别表示全 pass、有 flag 或 uncertain、有错误、未发送。`warning/blocker` 目前只是结果标签，不改变退出码；不能把退出码 1 自动解释成应禁止发布。

reader-first 默认不调用本工具；只有用户明确接入机器审核 hook 后，才由该 hook 使用 reader-first 自带的 `references/rule.md` 调用 runner。配置环境变量或安装 AGENTS 写作规则均不代表启用。用户直接要求 typed-review 执行一次检查仍按本 skill 的执行流程处理，不因此创建持久 hook。它的写作规则、安装行为和最终裁决不依赖本工具。只有用户要求改写时才修改原文，不自动部署 hooks、CI 或发布门槛。
